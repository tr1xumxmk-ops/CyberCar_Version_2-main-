02 /What each part does — and why it is used

LOLIN S2 Mini (ESP32-S2)

The controller and Wi-Fi access point. It hosts the captive portal at http://192.168.4.1/, validates local control requests, then sets motor-driver GPIO signals. The phone connects to the car’s own Wi-Fi network; this is local control, not Internet service.

Control logicWi-Fi APHTTP server

L298N dual H-bridge

Motor current must not be supplied by ESP32 GPIO pins. The L298N switches external motor power according to IN1–IN4 and ENA/ENB. It loses some voltage as heat, so make sure the motors and driver can handle the actual load.

Motor power stageDirection

2S LiPo + power switch

The battery feeds the motor driver and the 5V buck converter. Use an appropriate LiPo charger, low-voltage protection/monitoring, a secure connector, and a physical disconnect. A 2S pack is about 7.4 V nominal and 8.4 V fully charged.

Portable supplyPhysical shutoff

5V buck converter

Reduces the battery voltage to a regulated 5.00 V rail. A servo can draw brief current spikes, so size the converter for the controller and servo together. Never connect the buck output to the ESP32 3V3 pin.

Regulated logic railServo supply

Ball / grip servo

GPIO 13 carries the command signal, while the servo is powered by the separate 5V rail. Do not power a servo from an ESP32 GPIO. Add local decoupling near the servo if resets occur during motion.

Mechanical actuator

RGB LED + piezo

They communicate state without requiring the phone screen: idle, driving, and emergency stop can have different colors and tones. Each LED channel needs its own current-limiting resistor. A high-current buzzer needs a driver stage.

User feedbackDebugging

03 /Understand the code before upgrading it

The project is split into small files on purpose. The pin table in the diagram must always match config.h; if you change a GPIO in code, update the diagram and wiring notes too.

config.h — single source of truth

Stores SSID/password, GPIO assignments, timing constants, speed profiles, and command enums. Use constexpr for fixed compile-time values. Don’t make changing state (current command, emergency latch, uptime) constexpr.

namespace Config {
  constexpr uint8_t MOTOR_IN1_PIN = 7;
  constexpr uint8_t MOTOR_IN2_PIN = 6;
  constexpr uint8_t MOTOR_IN3_PIN = 4;
  constexpr uint8_t MOTOR_IN4_PIN = 5;
  constexpr uint8_t MOTOR_ENA_PIN = 11;
  constexpr uint8_t MOTOR_ENB_PIN = 12;
  constexpr uint8_t BALL_SERVO_PIN = 13;
}

motor_driver.h — one job

Owns pin initialization and translates Forward/Backward/Left/Right/Stop/Brake to H-bridge inputs. Keeping it separate makes the motor logic testable without mixing it with web HTML.

motors.apply(DriveCommand::Forward, millis());
motors.tick(millis());
// ENA and ENB: digital HIGH/LOW only.
// Medium/Slow are timed bursts, not smooth motor voltage control.

captive_portal.h — UI + API boundary

Starts the local Wi-Fi AP, serves the HTML, provides a small JSON state endpoint, and validates control requests. The portal is local HTTP; don’t port-forward it to the public Internet. Browser session checks improve request hygiene, but HTTP is not encrypted.

GET  /api/state
POST /api/joy?x=…&y=…
POST /api/speed?level=slow|medium|fast
POST /api/brake
POST /api/resume

CyberCarPro_optimized.ino — orchestration

Creates the hardware objects, starts the watchdog and portal, services incoming HTTP requests, then updates the car using a fresh millis() timestamp. Keep the main loop short and avoid long delay() calls or blocking sensor work.

void loop() {
  esp_task_wdt_reset();
  portal.update();
  car.update(millis());
  delay(4);
}
Speed truth: FAST holds ENA/ENB HIGH; MEDIUM and SLOW use low-rate digital on/off windows, not hardware LEDC PWM. They may pulse or jerk. To get smooth speed control, use hardware PWM or a proper motor voltage controller; ordinary static HIGH/LOW outputs cannot provide three smooth speeds.
Operational limitation: This build does not perform environment-aware stopping. Test in a clear, supervised area and keep a physical battery disconnect accessible; a software timeout is not a substitute for physical safety.

05 /Secure backend & JSON injection defense

The ESP32 is the local backend in this offline-first design: the browser calls bounded HTTP endpoints, and firmware verifies the session, trusted origin, argument types, and allowed command values before changing hardware. The new secure_backend.h centralizes these rules.

Validation, not trust

Joystick values are strict bounded integers (-100 to 100); speed and servo actions are fixed allowlists. Unknown actions are rejected, not executed. No request value is treated as C++ code, JavaScript, or an arbitrary JSON fragment.

JSON injection defenses

State responses contain only fixed enum names, booleans, and integers. Never concatenate arbitrary browser text into a JSON response. If a future endpoint must return user-controlled text, escape it with SecureBackend::escapeJsonString or use a reviewed serializer.

Session and request checks

A PIN gate issues a random session token in an HttpOnly, SameSite=Strict cookie; mutating requests require the expected local Origin. Login attempts are temporarily blocked after repeated failures, API calls are rate-limited, and the motor command watchdog stops movement after lost keepalives.

Limits to understand

The captive portal uses HTTP, not TLS. It is intended only for a private direct Wi-Fi link; do not port-forward it or expose it publicly. PIN authentication is an extra barrier, not a replacement for encrypted transport on an Internet service.

06 /Robot face expressions without wasting memory

The live dashboard draws the face as one inline SVG, then switches a small state name when the car is idle, moving, boosting, or braking. No portrait image is repeatedly downloaded, and no large animation file is stored in RAM.

Best format

For neon line art, use SVG paths or a tiny 64×64 one-bit bitmap. Avoid full-screen PNG/JPEG files. The included editable assets are in CyberCar/CyberCarPro_optimized/web_assets/faces/.

Where to put custom faces

For this build, copy the few vector paths into the single robotFace SVG in captive_portal.h. Separate image files require LittleFS setup; if you later enable it, place them under data/faces/ and serve them by a fixed allowlisted path.

Recommended states

idle, forward, backward, left, right, fast, brake, and error. Use one face display and swap the expression rather than mounting eight images simultaneously.

Memory rule

A raw 64×64 one-bit bitmap uses 512 bytes of pixel data. Keep the assets simple, avoid large blur filters, and run CSS animations on the phone browser. ESP32 should serve small HTML/SVG and status JSON, not frames of video.

07 /A practical roadmap toward a greater robot

Phase A — reliable basics

Verify forward/reverse/left/right, make motor polarity consistent, add a physical emergency power switch, secure the battery, and measure free heap during portal activity.

Must work every time

Phase B — instrumentation

Add battery voltage monitoring with a correctly calculated divider and calibrated ADC scaling; log low-voltage state. Add the selected future sensor only after defining a clear interface and a safe default behavior.

Measure before adding AI

Phase C — smarter motion

Add wheel encoders for speed/distance estimates, a motion state machine, controlled acceleration, and a timed route recorder. Save short waypoints, not video or huge arrays in RAM.

Repeatable movement

Phase D — smarter sensing

Add distance sensors or a camera only after choosing the compute board and power budget. The ESP32-S2 is well suited to control/UI but has limited RAM for large neural-network models.

Edge constraints

Phase E — AI assistance

Start with small rule-based behaviors or a tiny quantized classifier, collect labelled examples, validate in a safe test area, and retain a deterministic stop path independent from the model.

AI is not the safety layer

Phase F — competition readiness

Prepare a demo checklist, spare battery, spare wires, versioned firmware, a one-page block diagram, clear failure recovery, and logs proving each feature. Design for repair as much as appearance.

Reliability + presentation

Move the car without consuming much memory

  • Keep motor movement command-driven: one enum + timestamps instead of storing motion frames.
  • For repeatable routes, store a small fixed list of commands and durations in flash/PROGMEM, not a dynamic vector of thousands of samples.
  • Use a finite-state machine such as IDLE → DRIVE → TURN → STOP, updated using millis(); don’t block the web server with long delays.
  • Keep the live UI CSS-animated in the phone browser. The ESP32 should send a small status JSON object, not animation images.
  • For learning-based movement, train off-device, then deploy only a compact model if the board’s memory and latency are sufficient.

08 /Pre-power checklist

Lift all wheels off the floor. Put the physical battery switch in OFF.
Check battery polarity and confirm the motors are rated for the supply voltage. Set the buck converter to 5.00 V with a multimeter before connecting it to the ESP32 or servo.
Remove L298N ENA/ENB jumper caps because GPIO 11/12 control the enables. Keep all grounds common.
Do not connect the L298N +5V terminal to the buck 5V rail without understanding the exact board’s regulator/jumper configuration. Never feed 5V into ESP32 3V3.
Power on and check Serial Monitor at 115200 baud. Test each direction briefly. If a wheel is reversed, swap that motor’s two output wires or change the relevant inversion constant.
Test EMERGENCY BRAKE and confirm that a separate resume action is required. The car must remain stationary at startup and on lost control commands.
Do not test on a table edge or near people. The software brake is not a physical power disconnect and cannot guarantee immediate stopping under every fault.
